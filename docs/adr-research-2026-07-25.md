# Proposed ADRs

An audit of decisions already embedded in this codebase that have no ADR. Every claim about the code cites `file:line`; every claim about a platform constraint cites a first-party doc.

## The convention observed in ADR 0001

`docs/adr/0001-generic-extension-name-buildkite-display-name.md` is the only existing ADR, and `AGENTS.md:19-49` states the rules it follows. Matching it means:

- **Filename**: `NNNN-slug.md`, zero-padded to four digits, sequential. To add one, scan the directory for the highest number and increment (`AGENTS.md:21`).
- **Title**: a single `#` H1 stating the decision, not a ticket ID — "Generic extension name, provider-specific display name". Not "ADR 0001: ...".
- **Body**: prose paragraphs, no template. `AGENTS.md:37` — "A single paragraph is a complete ADR. The value is recording *that* a decision was made and *why*, not filling out sections." ADR 0001 runs to two paragraphs: the constraint and the decision, then a secondary naming rationale.
- **Optional sections, in this order**: `## Considered Options` (a bulleted list where each bullet is **bolded option** — em-dash — why it lost) and `## Consequences` (one paragraph on non-obvious downstream effects). `AGENTS.md:45` — add each "only when" it earns its place; "Most ADRs need neither."
- **No Status line** unless the decision is actually revisited (`AGENTS.md:45`), and no date, author, or "Context/Decision/Consequences" headers.
- **Bar for writing one** (`AGENTS.md:25-31`): hard to reverse **and** surprising without context **and** a real trade-off. All three, or skip it.

The proposals below are numbered from `0002`. They are proposals, not ADRs — each one ends with the question only the repo author can answer, because the "why" is not recoverable from the code.

## 0002 — Talk to Buildkite through the `bk` CLI subprocess, not the REST or GraphQL API

**The decision as it stands in the code.** Every Buildkite interaction shells out to the `bk` binary. `src/buildkite/client.ts:189` probes `bk --version`; `client.ts:222` runs `bk whoami`; `client.ts:233` runs `bk auth login --scopes "read_only"`; `client.ts:242-244` runs `bk build list --pipeline … --branch … --json --limit 1`; `client.ts:262-264` runs `bk build view … --pipeline … --json`; `client.ts:284-296` spawns `bk job log <id> -p <pipeline> -b <build>`. The extension will even install the CLI for the user — `winget install buildkite.bk` on Windows, `brew install buildkite/buildkite/bk@3` otherwise (`client.ts:201-207`). Absence of the CLI is a first-class UI state (`src/buildkite/module.ts:179-183`, `module.ts:478-485`). The JSON that comes back is snake_case REST payload shape, re-mapped by hand in `client.ts:336-365` (`raw_log_url`, `web_url`, `pipeline.slug`), and URLs are parsed back apart with REST-path regexes in `client.ts:90-108` and `client.ts:110-128`. There is no HTTP client anywhere in `src/`, and `package.json` declares no runtime `dependencies`.

**Plausible alternatives.** (a) The REST API directly — `GET /v2/organizations/{org}/pipelines/{slug}/builds?branch=…` is exactly the query being made, and `raw_log_url` on each job is exactly the log the extension fetches; the code already knows both URL shapes (`client.ts:94`, `client.ts:114`). (b) The GraphQL API, which would fetch build + jobs + triggered-build chain in one round trip instead of the loop in `src/buildkite/jobAnalyzer.ts:79-100`. (c) A hybrid: CLI for auth (`bk auth token` prints the stored token) and HTTP for data.

**The constraint that grounds it.** The REST API authenticates with a bearer token the caller must obtain and store itself — "To authenticate an API call using an access token, set the Authorization HTTP header to the word Bearer, followed by a space, followed by the access token" (https://buildkite.com/docs/apis/rest-api). GraphQL tokens are *worse* for a least-privilege story: "Since the scopes of these API access tokens cannot be restricted…" (https://buildkite.com/docs/apis/graphql-api). The CLI, by contrast, does OAuth and owns a credential store (`--credential-store="auto" | keyring | shm`) and supports scoped login (`bk auth login --scopes read_only`) — https://buildkite.com/docs/platform/cli/reference/auth. Choosing the CLI buys the whole auth problem for free; it costs a hard install prerequisite, which is why `client.ts:197-219` exists.

**Note on a fact worth re-checking.** `bk whoami` (`client.ts:222`) is not among the documented `bk` v3 command categories — the reference lists `agent, api, artifacts, auth, browse, build, cluster, config, configure, init, job, maintainer, organization, package, pipeline, preflight, queue, secret, skill, update, user, version` (https://buildkite.com/docs/platform/cli/reference). The documented equivalent is `bk auth status`. Since the extension installs `bk@3` (`client.ts:206`) and treats a non-zero exit from `bk whoami` as "not authenticated" (`client.ts:221-229`), a removed or renamed command degrades silently into a permanent "Not authenticated with Buildkite" state (`module.ts:186-188`).

**Open question for the author.** Was the CLI chosen to avoid ever holding a Buildkite token (the auth argument), or to inherit a login the user already has — including org SSO, which `module.ts:493` hints at? The answer decides whether a future REST fallback is acceptable at all, or whether "never possesses a credential" is a property of the product.

## 0003 — Store no Buildkite credential; delegate auth entirely to the `bk` keychain

**The decision as it stands in the code.** There is no use of `vscode.SecretStorage`, no `context.secrets`, no token in settings, and no token prompt anywhere in `src/`. Authentication is a gate, not a state the extension owns: `module.ts:185-189` runs `whoami` and stops on failure; `module.ts:487-496` renders an "Authenticate to CLI" button; pressing it posts `bkCliAuth` (`media/main.js:8-10`) which runs `bk auth login --scopes "read_only"` (`module.ts:229-248` → `client.ts:231-238`). The only thing the extension persists is a job-state filter in `context.globalState` (`module.ts:147-150`, `module.ts:286-306`).

**Plausible alternatives.** (a) `vscode.SecretStorage` holding a Buildkite API token, prompting on first use. (b) A `contributes.configuration` setting for the token (bad, but common). (c) VS Code's `AuthenticationProvider` API to become a first-class auth source.

**The constraint that grounds it.** SecretStorage is available and would be the correct home for a token — "Represents a storage utility for secrets (or any information that is sensitive) that will be stored encrypted. The implementation of the secret storage will be different on each platform and the secrets will not be synced across machines" (https://code.visualstudio.com/api/references/vscode-api). It was not used. The delegated path is real: `bk` stores credentials in an OS keyring by default and supports scoped read-only login (https://buildkite.com/docs/platform/cli/reference/auth).

**Consequence already visible in the repo.** `README.md:33`, `README.md:49`, `README.md:116` and `README.md:124` all tell the user "You'll be prompted for your Buildkite API token on first use" / "Enter your Buildkite API token when prompted", and `README.md:16` and `README.md:66` list a Buildkite API token as a prerequisite. No such prompt exists in the code. Either the README describes a design that was replaced, or it describes an intent the CLI path silently satisfies. This is the single largest doc/code divergence in the repo.

**Open question for the author.** Was SecretStorage considered and rejected (because holding a token is a liability, or because `bk` had to be installed anyway), or was it never on the table because the CLI came first? And is the README stale, or is a direct-token path still intended as a fallback for users who can't install `bk`?

## 0004 — Repo directory name is the Buildkite pipeline slug

**The decision as it stands in the code.** `src/extension.ts:50-53` reads `git config --get remote.origin.url` (`src/utils.ts:10-25`), extracts the trailing path segment before `.git` with `/[:\/]([^\/:]+)\.git$/` (`utils.ts:45-48`), and assigns it to `bkModule.repoName`. That value is passed straight into `new BuildkiteClient(this.repoName, this.currentBranch)` (`module.ts:174-177`, `module.ts:470-473`) where the first constructor parameter is named `pipelineSlug` (`client.ts:78`, `client.ts:81`) and is interpolated into `--pipeline` (`client.ts:243`, `client.ts:261-264`). Branch comes from `git rev-parse --abbrev-ref HEAD` (`utils.ts:27-43`). There is no override: `package.json` has no `contributes.configuration` block at all.

**Plausible alternatives.** (a) A `buildDetective.pipelineSlug` setting, defaulting to the repo name. (b) Resolving the pipeline by matching its `repository` field against the git origin, which the REST pipeline resource exposes. (c) Prompting once and caching the choice in `globalState` next to the filter.

**The constraint that grounds it.** `bk`'s `--pipeline` flag takes "a {pipeline slug} or in the format {org slug}/{pipeline slug}" (https://buildkite.com/docs/platform/cli/reference/build). A Buildkite pipeline slug derives from the pipeline's *name*, which is independent of the repository it builds — one repo can back several pipelines, and a pipeline can be named anything. So repo-name-equals-slug is a convention, not a platform guarantee.

**Consequence already visible in the code.** When the assumption fails, the failure is indistinguishable from "nothing to show": `getLatestBuild` swallows the error and returns `undefined` (`client.ts:250-253`), which renders "No builds found for this branch." (`module.ts:518`) — not "no pipeline named X". The only path that names the real problem is the 404 branch in `module.ts:568-570`, which cannot fire because `getLatestBuild` never rethrows. A user with a mismatched slug sees a working-looking, permanently empty panel.

**Open question for the author.** Is zero-config the point — the extension should work with no setup or die quietly — or is this an unexamined artifact of the author's own repos where slug and repo name happen to match? That determines whether the fix is a setting, a discovery step, or a better error message.

## 0005 — Failure detection is a hand-rolled log slice: first ` Error:` back to the nearest section header

**The decision as it stands in the code.** `BuildkiteClient.extractErrorSnippets` (`client.ts:130-159`) splits the log into lines, finds the **first** line matching `/ Error:/` (`client.ts:138`), walks backwards to the nearest line matching `/^\[\d{1,2}:\d{2}:\d{2}\s+(?:AM|PM)\]\s*---/` (`client.ts:136`, `client.ts:143-149`), and falls back to 50 lines before the match if no section header is found (`client.ts:150-152`). Only that slice is sent to any assistant (`module.ts:375`, `jobAnalyzer.ts:111-112`, `jobAnalyzer.ts:219`). The timestamp format that regex depends on is itself synthesised by the extension: `normalizeLogTimestamps` (`client.ts:161-185`) rewrites Buildkite's `\x1b_bk;t=<epochMs>\x07` markers into `[H:MM:SS AM]` via `toLocaleTimeString('en-US', … hour12: true)`, and is applied to every log before slicing (`client.ts:327`). When the slice is empty the user gets "No errors found in log." (`module.ts:371`) even though the job failed.

**Plausible alternatives.** (a) Send the whole log and let the model find the failure. (b) Return every ` Error:` region, not just the first. (c) Let the CLI do it — `bk job log --agent` exists and is documented as "Format output to be optimal for LLM consumption (strips ANSI, deduplicates loops)", with `--no-window` described as disabling "failure-focused windowing in --agent output" and `--max-tokens` capping the result (https://buildkite.com/docs/platform/cli/reference/job). That is, the CLI now ships the exact capability this function hand-rolls, including the log-slimming and the timestamp stripping (`--no-timestamps`).

**The constraint that grounds it.** Sending the whole log is not free: "The recommended GPT-4o model has a limit of 64K tokens. The returned model object from the selectChatModels call has a `maxInputTokens` attribute that shows the token limit" (https://code.visualstudio.com/api/extension-guides/language-model). CI logs routinely exceed that, so *some* windowing is mandatory — the ADR-worthy part is that the window is hand-cut on an English-locale timestamp the extension itself printed, rather than delegated.

**Open questions for the author.** Was `bk job log --agent` unavailable when this was written, or rejected because the slice needs to be *shown* to the user verbatim (`jobAnalyzer.ts:260`) and `--agent` output is not that? And is first-error-only deliberate (the first failure usually causes the rest) or an unnoticed consequence of `findIndex`?

## 0006 — Sidebar is a WebviewView with server-rendered HTML strings, not a TreeView

**The decision as it stands in the code.** `package.json:47-56` declares the view with `"type": "webview"`, and `module.ts:96-101` registers it via `registerWebviewViewProvider`. All markup is built by string concatenation in TypeScript: `getSidebarHtml` (`module.ts:577-614`), the job list (`module.ts:533-566`), the settings screen (`module.ts:405-438`). Presentation lives in `media/style.css` (396 lines, themed with `--vscode-*` variables), interaction in `media/main.js` (82 lines of `postMessage`), and the filter chips use bundled PNGs — `media/icons/icon_eye.png`, `icon_eye_slash.png` (`media/style.css:363-388`) — rather than codicons. Escaping is manual: `escapeHtml` (`utils.ts:133-141`) applied at `module.ts:550`, `module.ts:556-557`, `jobAnalyzer.ts:260`, `jobAnalyzer.ts:279`.

**Plausible alternatives.** (a) A `TreeView` — the contribution-points doc describes exactly two ways to fill a view: "With a TreeView by providing a data provider… TreeViews are ideal for showing hierarchical data and lists" versus "With a WebviewView by registering a provider with registerWebviewViewProvider" (https://code.visualstudio.com/api/references/contribution-points). Builds→jobs is hierarchical data with a list of per-item actions — the canonical TreeView shape, and `view/item/context` menus would give the two per-job buttons for free. (b) A hybrid: TreeView for the job list, webview panel only for the analysis. (c) The Testing API, which is what `"categories": ["Testing"]` (`package.json:11-13`) claims the extension is.

**The constraint that grounds it.** VS Code's own guide is explicit: "Webviews are pretty amazing, but they should also be used sparingly and only when VS Code's native API is inadequate. Webviews are resource heavy and run in a separate context from normal extensions. A poorly designed webview can also easily feel out of place within VS Code" (https://code.visualstudio.com/api/extension-guides/webview). Choosing a webview anyway is exactly the "surprising without context" case ADR 0001's own criteria (`AGENTS.md:28`) call out.

**Open question for the author.** What could a TreeView not do — the multi-select filter chips, the two-button-per-job row, the auto-refresh banner, or something about how it looked? If the answer is "nothing in particular", that's worth knowing before the next person spends a week porting it.

## 0007 — Two assistant paths: Copilot/Cursor answers render in-panel, Claude is handed off out of the extension

**The decision as it stands in the code.** The UI shows two buttons on every failed job (`module.ts:555-558`), labelled dynamically — "Ask Cursor" when `vscode.env.appName === 'Cursor'`, else "Ask Copilot" (`utils.ts:167-169`) — plus a fixed "Ask Claude". They do fundamentally different things.

*Path A (`askIde`, `module.ts:322-347`)* opens a `BuildkiteJobAnalyzer` webview panel (`jobAnalyzer.ts:154-160`), resolves the errors, calls the VS Code Language Model API, streams the response into a string (`jobAnalyzer.ts:47-51`), and renders it inside the panel as escaped plain text (`jobAnalyzer.ts:279`). Model selection is unfiltered — `vscode.lm.selectChatModels()` with no selector (`jobAnalyzer.ts:314`) — then picks the first model whose id contains `'auto'`, else the first model at all (`jobAnalyzer.ts:34`). If no models exist, it copies the prompt and tells the user to paste it (`jobAnalyzer.ts:21-32`), and in Cursor it degrades the warning to a 10-second status-bar message rather than a modal (`jobAnalyzer.ts:317`).

*Path B (`askClaude`, `module.ts:349-383`)* never opens a panel. It builds the prompt and calls `askClaude` (`claudeIntegration.ts:22-50`), a three-rung ladder: if the `anthropic.claude-code` extension is installed, invoke its command `claude-vscode.editor.open` with the prompt (`claudeIntegration.ts:26-29`); else if `which claude` / `where claude` finds a binary (`claudeIntegration.ts:52-63`), write the prompt to a temp file and pipe it into a terminal, with `cmd /c` quoting on Windows (`claudeIntegration.ts:31-43`); else copy to clipboard and say so (`claudeIntegration.ts:45-49`).

**Plausible alternatives.** (a) One button that picks the best available assistant. (b) Render Claude's answer in the same analysis panel by capturing its output rather than handing off. (c) Register a Chat Participant so both live in the editor's chat surface. (d) Filter models with `selectChatModels({ vendor: 'copilot' })` instead of taking whatever is first.

**The constraint that grounds it.** Two facts from https://code.visualstudio.com/api/extension-guides/language-model justify the shape: "Copilot's language models require consent from the user before an extension can use them. Consent is implemented as an authentication dialog. Because of that, selectChatModels should be called as part of a user-initiated action, such as a command" — hence a button, not automatic analysis. And: "If your extension already contributes functionality other than using the Language Model API, we recommend that you do not introduce an extension dependency on GitHub Copilot in the extension manifest. This ensures that extension users that do not use GitHub Copilot can use the non language model functionality… Make sure to have appropriate error handling when accessing language models for this case." `package.json` correctly declares no `extensionDependencies`, and the empty-models branch is the recommended error handling. The Claude path has no equivalent API, which is why it is a subprocess/command handoff instead.

**A deliberate deviation already recorded in a test, not an ADR.** `src/buildkite/jobAnalyzer.test.ts:70-74` asserts that request options stay empty, with the reason inline: `'toolMode must not be set — passing Auto causes the stream to hang when the model makes a tool call'`. That is a hard-won platform workaround (`jobAnalyzer.ts:37-45` passes `{}`) surviving only as a test assertion — precisely the "deliberate deviation a reader would otherwise fix" that `AGENTS.md:33` says deserves an ADR.

**Open questions for the author.** Why does Claude's answer never come back into the extension's own panel while Copilot's does — is that a capability gap, or a deliberate "Claude is a full agent, let it own the session" stance? And is picking the first model whose id contains `'auto'` (`jobAnalyzer.ts:34`) a real preference for auto-routing models, or a heuristic that happened to work?

## 0008 — Re-render the whole webview HTML on every state change instead of message-passing

**The decision as it stands in the code.** Data flows extension→webview exclusively by reassigning `webview.html`. Every one of `module.ts:156`, `module.ts:201`, `module.ts:399`, `module.ts:406`, `module.ts:505` and `jobAnalyzer.ts:186`, `:199`, `:209`, `:216`, `:223` rebuilds the entire document. `media/main.js` only sends messages the other way (`media/main.js:3-82`). The analysis panel re-renders up to four times for a single click (loading → errors → analysing → result). Nothing uses `getState`/`setState`, `retainContextWhenHidden`, or `localResourceRoots` — none appear anywhere in `src/`.

**Plausible alternatives.** (a) Set `webview.html` once and push updates with `postMessage`, patching the DOM in `media/main.js`. (b) Keep whole-document rendering but persist UI state with the webview state API.

**The constraint that grounds it.** The webview guide states the cost plainly: "Setting webview.html replaces the entire webview content, similar to reloading an iframe. This is important to remember once you start using scripts in a webview, since it means that setting webview.html also resets the script's state." Its recommendation for exactly this situation: "The best way to solve this is to make your webview stateless. Use message passing to save off the webview's state and then restore the state when the webview becomes visible again." It also notes `getState`/`setState` "are the preferred way to persist state, as they have much lower performance overhead than retainContextWhenHidden" (https://code.visualstudio.com/api/extension-guides/webview).

**Consequence already visible in the repo.** The `SettingsDetailsOpen` class (`module.ts:58-68`) and the `settingsDetailsToggle` message round-trip (`media/main.js:71-81` → `module.ts:318-320` → `module.ts:410`, `module.ts:422`) exist for one reason: to re-derive whether a `<details>` element was open, because re-rendering destroys it. That is the tax the guide predicts, already paid, for a single expandable section. Every additional piece of client state will need the same round trip.

**Open question for the author.** Is server-rendered-string simplicity the deliberate trade (no client framework, no DOM diffing, everything reviewable in one function), with flicker and lost scroll position accepted? Or did this start as one-shot rendering and simply never get revisited as the UI grew?

## 0009 — Provider seam is a directory, not an interface

**The decision as it stands in the code.** `CONTEXT.md:21-23` defines a Provider as living "behind its own module under `src/`, exposing the same shape to the rest of the extension". `AGENTS.md:33` names "the provider seam (how a new CI system gets added)" as a thing that qualifies for an ADR. ADR 0001 asserts it already works: "provider-specific work is already isolated behind a module (`src/buildkite/`) and the rest of the extension is provider-agnostic" (`docs/adr/0001-generic-extension-name-buildkite-display-name.md:3`).

The code delivers this partly. `src/buildkite/` does hold the Buildkite specifics (`client.ts`, `jobAnalyzer.ts`, `module.ts`) and the `Bk*` types stay inside it. But there is no interface: `src/extension.ts:5` imports the concrete `BuildkiteSidebarViewProvider` and `extension.ts:11` constructs it directly; nothing declares the "same shape" a second provider would implement. And provider-specific knowledge has leaked outward and inward:

- `src/utils.ts:61-121` — a 40-entry emoji shortcode map documented as covering "the most frequently seen ones in Buildkite job names" (`utils.ts:62`), living in the shared utils module.
- `src/buildkite/module.ts` is simultaneously the Buildkite adapter and the entire sidebar UI, status bar, polling loop, settings screen, and message router (702 lines) — so "add a provider" currently means "reimplement the UI".
- `src/buildkite/jobAnalyzer.ts:54-61` hard-codes "These are Buildkite job errors" into the prompt shared by both assistant paths.
- `src/claudeIntegration.ts` is provider-agnostic and correctly sits at the root; `src/utils.ts:143-165` (webview resource URIs) likewise.

**Plausible alternatives.** (a) Define the provider interface now — `getLatestBuild()`, `getJobLog()`, `isAvailable()`, `authenticate()` — and have `extension.ts` select an implementation. (b) Keep the UI in a provider-agnostic module and let providers supply only data. (c) Accept a single provider and delete the aspiration.

**Open question for the author.** What is the intended seam — a TypeScript interface each provider implements, or just "a folder, and we'll factor it out when a second provider actually arrives"? ADR 0001 already spent the marketplace-naming decision on the assumption that this seam is real, so it's worth writing down which of the two was meant.

## 0010 — Poll every 20 seconds, and only while the build is running

**The decision as it stands in the code.** `module.ts:25-26` fixes the interval at 20 seconds. `module.ts:682-692` installs a single `setInterval` (guarded against duplicates at `module.ts:683-685`) that refreshes only when the cached build state is in `RUNNING_STATES` — `running`, `failing`, `canceling` (`client.ts:55-59`). Otherwise the timer fires and does nothing; the UI calls this "paused" (`module.ts:132-137`, `module.ts:427-429`, `module.ts:529-531`). Event-driven refreshes complement it: `extension.ts:20-35` watches the Git extension's `repo.state.onDidChange` and calls `onBranchChange` / `onCommitChange` (`module.ts:660-680`). The interval is cleaned up in `dispose` (`module.ts:694-701`), wired to extension deactivation at `module.ts:104`.

**Plausible alternatives.** (a) Buildkite webhooks — structurally unavailable, since a webhook needs a publicly reachable endpoint and this runs on a developer's laptop. (b) Backoff (fast while running, slow otherwise). (c) A user-configurable interval — impossible today because there is no `contributes.configuration`. (d) Polling only while the sidebar is visible; note the code explicitly chooses the opposite, keeping polling and the status bar alive after the view is disposed (`module.ts:387-392`).

**The constraint that grounds it.** Buildkite's REST limits are "a rate limit of 200 requests per minute for each organization… the cumulative limit of all API requests made by users in an organization" plus a per-user default of "50 requests per minute", with either overage returning 429 (https://buildkite.com/docs/apis/rest-api/rate-limits). A 20-second interval is 3 req/min per developer per repo — comfortable alone, but it is a shared org budget, and the extension implements no 429 handling: `getLatestBuild` catches everything and returns `undefined` (`client.ts:250-253`), which surfaces as "No builds found for this branch." (`module.ts:518`). Buildkite also specifically recommends `exclude_jobs=true` "when polling build state" (https://buildkite.com/docs/apis/rest-api/builds) — the `bk build list` path fetches embedded jobs on every poll, which is heavier than needed for the status-bar update in `module.ts:194-196`.

**Open question for the author.** Where did 20 seconds come from — measured against `bk` latency, or a guess? And is the run-only gate a rate-limit concession or a battery/CPU one? That determines whether the right evolution is backoff, a setting, or nothing.

## 0011 — Distribute `.vsix` via GitHub Releases; never publish to the Marketplace

**The decision as it stands in the code.** `scripts/release.sh` is the whole release process: preflight (clean tree, on `main`, in sync with origin, non-empty `[Unreleased]` in `CHANGELOG.md`, tests green — `release.sh:19-53`), interactive semver bump (`release.sh:59-80`), rewrite `package.json` and promote the changelog heading (`release.sh:86-106`), commit + tag + push (`release.sh:111-127`), `vsce package --no-dependencies` (`release.sh:119`), then `gh release create` with the `.vsix` attached (`release.sh:133-136`) and the local artifact deleted (`release.sh:141`). `vsce publish` appears nowhere in the repo. `README.md:11-49` documents install as "download the `.vsix` → Install from VSIX". `scripts/install-local.sh` does the same for local dev, installing into both `code` and `cursor` if present (`install-local.sh:39-53`).

**Plausible alternatives.** (a) `vsce publish` to the VS Code Marketplace. (b) Open VSX, which is what Cursor and other forks actually read. (c) Both, from the same script.

**The tension worth recording.** ADR 0001's entire argument is about Marketplace identity — "The VS Code Marketplace treats `publisher.name` as an extension's permanent identity" and "Discoverability now depends entirely on `displayName`, `description`, and `keywords`… all indexed by marketplace search" (`docs/adr/0001-generic-extension-name-buildkite-display-name.md:3`, `:15`). Those consequences are currently hypothetical: nothing is listed. Meanwhile the rename commit reasoned that IDs were "free to change… while the extension is still unpublished" (`git show d0696bd`). Whether that freedom still exists is exactly the fact a future reader needs.

**Open question for the author.** Is Marketplace publishing intended-but-not-yet-done, blocked (publisher verification, Cursor-first audience), or declined on purpose? And if Cursor is a first-class target (`install-local.sh:47-52`, `utils.ts:167-169`, `jobAnalyzer.ts:24-31`), does Open VSX belong in `release.sh`?

## 0012 — Shell-interpolated `exec` everywhere except job logs, which use `spawn(shell: false)`

**The decision as it stands in the code.** Most subprocess calls go through `promisify(cp.exec)` — i.e. through a shell — with values interpolated into the command string: `client.ts:242-244` interpolates `this.pipelineSlug` and `this.branch`; `client.ts:262-264` interpolates a build number and pipeline slug; `utils.ts:15-17` and `utils.ts:32-34` run git with a `cwd` taken from the workspace folder. Exactly one call does it the safe way: `getJobLog` uses `cp.spawn('bk', [...args], { shell: false })` (`client.ts:284-296`).

The interpolated values are not extension-controlled. `pipelineSlug` is the repo directory name parsed by `/[:\/]([^\/:]+)\.git$/` (`utils.ts:46`) — that character class excludes `/` and `:` but permits `;`, `$`, `` ` ``, `&`, and spaces. `branch` is raw `git rev-parse --abbrev-ref HEAD` output (`utils.ts:32-34`). A branch or clone directory named to include shell metacharacters is executed as a shell command. The `claudeIntegration.ts:37-41` terminal command quotes its path (`'…'` on POSIX, `cmd /c ""…""` on Windows) — that path comes from `which`/`where` (`claudeIntegration.ts:52-63`), so it is a lesser exposure, but it shows quoting was on the author's mind in one place and not others.

**Plausible alternatives.** (a) Use `execFile`/`spawn` with an argv array everywhere, as `getJobLog` already does. (b) Validate branch and slug against a conservative pattern before interpolating. (c) Keep `exec` and quote explicitly.

**Open question for the author.** Was `spawn(shell: false)` in `getJobLog` a deliberate hardening, or just the natural way to stream a large log incrementally (`client.ts:301-307`)? If it was hardening, the other four call sites are an oversight worth an ADR *and* a fix; if it was streaming, then nobody has yet decided how untrusted branch names should be handled.

## 0013 — Zero runtime dependencies, `tsc`-only build, no bundler

**The decision as it stands in the code.** `package.json` has no `dependencies` key — only `devDependencies` (`package.json:68-80`). The build is `tsc -p ./` (`package.json:60`) emitting to `out/` (`tsconfig.json:5`) with `main` pointing at `./out/extension.js` (`package.json:26`). No esbuild, webpack, or rollup config exists. Both packaging paths pass `--no-dependencies` (`release.sh:119`, `install-local.sh:35`). `.vscodeignore` strips sources, tests, scripts, docs, and `node_modules/**` (`.vscodeignore:1-20`). `tsconfig.json` is strict (`tsconfig.json:9`), `module: Node16`, `target: ES2024`. Toolchain is pinned outside npm: `.mise.toml:2-3` (Node 25.9.0, pnpm 11.13.0) plus `"packageManager": "pnpm@11.13.0"` (`package.json:81`).

**Plausible alternatives.** (a) Bundle with esbuild, which VS Code recommends and the scaffold links to — "Reduce the extension size and improve the startup time by bundling your extension" (`vsc-extension-quickstart.md:41`, https://code.visualstudio.com/api/working-with-extensions/bundling-extension). (b) Take runtime dependencies (an HTTP client, a markdown renderer) and bundle them. (c) `tsc` plus `--no-dependencies` — the current state, which is only correct *because* the dependency count is zero.

**Consequences worth recording.** `--no-dependencies` is safe by construction today and silently wrong the day a runtime dependency is added, with no test to catch it. And the no-markdown-renderer choice is visible in the product: the LLM's answer is escaped and dumped as plain text (`jobAnalyzer.ts:279`), so markdown arrives as literal `##` and backticks.

**Also worth a look while writing this up.** `package.json:72` and `:78` alias the compiler in an unusual way — `"@typescript/native": "npm:typescript@^7.0.2"` and `"typescript": "npm:@typescript/typescript6@^6.0.2"`. That is a deliberate-looking swap of two package identities, and nothing in the repo explains it.

**Open question for the author.** Is "no runtime dependencies" a rule (keeps the `.vsix` tiny, keeps the supply chain to zero, makes `--no-dependencies` correct), or just where the code happens to have landed? And what is the compiler aliasing for?

## 0014 — Tests run in a real Extension Host; testability bought with hand-written dependency objects

**The decision as it stands in the code.** `.vscode-test.mjs:3-5` points `@vscode/test-cli` at `out/**/*.test.js`, so `pnpm test` (`package.json:64`) downloads and launches a real VS Code and runs Mocha's TDD interface (`suite`/`test`) inside it — every test file uses `suite(...)` (e.g. `src/test/utils.test.ts:4`, `src/buildkite/client.test.ts:4`). There is no mocking library in `devDependencies` (`package.json:68-80`): no sinon, no proxyquire, no ts-mockito. Seams are hand-built instead — `ClaudeIntegrationDependencies` (`claudeIntegration.ts:8-18`) with a real-implementation factory at `claudeIntegration.ts:65-74`; `LanguageModelAnalyzerDependencies` (`jobAnalyzer.ts:9-15`); an injectable `execFn` parameter defaulting to the real `exec` (`client.ts:197-199`). Where no seam exists, tests mutate the runtime — `Object.defineProperty(process, 'platform', …)` in `client.test.ts:7`, `:27`, `:47` and `claudeIntegration.test.ts:112`.

**Plausible alternatives.** (a) Split: `node:test` or vitest for pure logic (`extractRepoName`, `extractErrorSnippets`, `renderEmojiShortcodes`, `getBuildStatusBarState` — none of which need VS Code), and `@vscode/test-cli` only for activation and contribution-point tests. (b) Add a mocking library and stop hand-writing dependency types. (c) Keep as-is.

**Consequences visible in the repo.** Test placement is inconsistent: `src/buildkite/*.test.ts` sit beside their sources while `src/test/utils.test.ts` and `src/test/claudeIntegration.test.ts` are in a separate folder — with `.vscode-test.mjs` matching both, nothing forces a choice. Coverage is thin where the logic is densest: `extractErrorSnippets` (the core heuristic, `client.ts:130-159`), `normalizeLogTimestamps`, `resolveJobErrors`'s triggered-build walk, and `renderEmojiShortcodes` have no tests at all; `module.test.ts` has exactly one assertion (`module.test.ts:5-10`). And `test:ci` wraps the run in `xvfb-run` (`package.json:65`) for a headless Linux CI, but the repo contains no `.github/workflows` — the CI script has no CI.

**Open questions for the author.** Is `src/test/` versus co-located a rule or an accident? Is "no mocking library, write the dependency object by hand" a deliberate design pressure (it forces small, injectable seams) or just inertia? And is the missing CI workflow intentional (release runs tests locally at `release.sh:51`) or a gap?

## 0015 — `BuildkiteClient.instance` static singleton as a service locator

**The decision as it stands in the code.** `client.ts:76` declares `static instance: BuildkiteClient | null = null`, and the constructor assigns the *first* instance ever constructed to it (`client.ts:82-84`) — later constructions do not replace it. `resolveJobErrors`, in a different module, reaches through that static rather than taking a client: `BuildkiteClient.instance?.getBuildDetails(...)` (`jobAnalyzer.ts:86-89`) and `BuildkiteClient.instance?.getJobLog(...)` (`jobAnalyzer.ts:106`). Meanwhile the owning module holds its own reference in `this.buildkiteClient` (`module.ts:122`) and keeps it fresh on branch change by *mutating* the existing object (`module.ts:474-476`) rather than constructing a new one — which is what keeps the singleton and the instance field from diverging.

**Plausible alternatives.** (a) Pass the client into `BuildkiteJobAnalyzer`, which already takes a constructor argument bag (`jobAnalyzer.ts:140-152`) and into `resolveJobErrors` as a parameter. (b) A module-level factory. (c) Keep the singleton but make it an explicit, documented registry.

**Consequences.** The `?.` at `jobAnalyzer.ts:86` and `:106` silently returns `null` from `resolveJobErrors` if the singleton was never set, which the UI reports as "No failed job found or could not fetch job log." (`module.ts:365`) — a null-client bug and a genuinely missing log are indistinguishable. It also quietly forecloses multi-root workspaces and multiple organizations: `extension.ts:40-47` watches *every* repository the Git extension knows about, but only one `BuildkiteClient` can ever be the instance.

**Open question for the author.** Was the static a deliberate service-locator (so free functions like `resolveJobErrors` stay parameter-light), or the quickest way to reach a client from `jobAnalyzer.ts` without threading it through? The multi-repo behaviour depends on the answer.

## 0016 — No `contributes.configuration`: the extension has no user settings

**The decision as it stands in the code.** `package.json:27-57` contributes commands, one view container, and one view — and nothing else. There is no `configuration` block, so `vscode.workspace.getConfiguration` appears nowhere in `src/`. Every tunable is either a constant (`AUTO_REFRESH_INTERVAL = 20`, `module.ts:25`; the default job-state filter, `client.ts:61-73`) or hidden state (`context.globalState` for the filter, `module.ts:147-150`, `module.ts:289-292`, `module.ts:300-304`). Notably `client.ts:68-72` keeps five states commented out rather than expressed as a default the user could change.

**Plausible alternatives.** (a) Settings for refresh interval, pipeline slug, and default filter. (b) Workspace-level settings so a monorepo can pin its pipeline. (c) Stay settings-free by design.

**Consequences.** Two of the highest-risk assumptions in this document — pipeline slug (0004) and refresh interval (0010) — have no escape hatch, so their failure modes are unrecoverable by the user. The counter-argument is real: a zero-setting extension has no configuration bugs and no migration burden, and the filter UI (`module.ts:405-438`) shows the author prefers in-product controls over the settings editor.

**Open question for the author.** Is "no settings" a product stance (it should just work, and anything that needs configuring is a design failure), or has nothing yet been contentious enough to warrant one? If it's a stance, that belongs in an ADR before the first `contributes.configuration` block lands.

## Where the code is ambiguous — deliberate or incidental, I could not tell

These are real observations that did not become proposals because I cannot distinguish a decision from an accident. Each is a question, not a finding.

1. **`"onWorkspaceContains:.git"` is not a documented activation event.** `package.json:24` lists it, but the reference documents the event as `workspaceContains:path` with no `on` prefix — "workspaceContains:path is emitted and interested extensions will be activated whenever a folder is opened and the folder contains at least one file that matches a glob pattern", example `"workspaceContains:**/.editorconfig"` (https://code.visualstudio.com/api/references/activation-events). As written it is inert. It is also redundant: `onStartupFinished` (`package.json:23`) already activates unconditionally — "emitted and interested extensions will be activated some time after VS Code starts up. This is similar to the `*` activation event, but it will not slow down VS Code startup" (same page). So the intent might be "always activate, cheaply" (achieved) or "activate only in git repos" (not achieved, and incompatible with the first entry). Which was meant is an ADR-sized question about activation cost; the current state answers it by accident.

2. **The webview `nonce` does not match its own CSP.** `module.ts:591` emits `script-src ${cspSource} 'nonce-${nonce}'` while `module.ts:596` writes `<script nonce="nonce-${nonce}" …>` — the element's `nonce` attribute should carry the bare value, not the `nonce-` prefix. The script still loads, because `cspSource` independently allows it, which is why nothing is visibly broken. Is the nonce defence-in-depth that's subtly misconfigured, or leftover scaffolding that could simply be deleted along with `getNonce` (`utils.ts:123-131`)?

3. **The analysis panel grants scripting it never uses.** `jobAnalyzer.ts:159` passes `{ enableScripts: true }`, but that panel's CSP is `default-src 'none'; style-src ${cspSource}` (`jobAnalyzer.ts:286`) with no `script-src`, and it loads no JS. The guide is explicit that "A webview should have the minimum set of capabilities that it needs. For example, if your webview does not need to run scripts, do not set the enableScripts: true" (https://code.visualstudio.com/api/extension-guides/webview). Copy-paste, or a placeholder for planned interactivity?

4. **`localResourceRoots` is never set** on either webview (`module.ts:214`, `jobAnalyzer.ts:156-160`, `utils.ts:54-56`), so both default to the extension folder *plus* the user's workspace folders. The guide recommends narrowing it: "If your webview does not need to load resources from the user's workspace, set localResourceRoots to [vscode.Uri.file(extensionContext.extensionPath)] or even []" (same page). Neither webview loads workspace files. Deliberate laziness or unexamined default?

5. **`openHtmlWebviewPanel` (`utils.ts:50-59`) is dead code** — exported, never imported. It creates a panel with a `customHtmlWebview` view type and no CSP. Is it a leftover from a panel-based UI that the sidebar replaced (`module.ts:74-83` still registers `openPanel` as a no-op "kept for compatibility"), or a deliberate escape hatch?

6. **`build-detective.openPanel` is a contributed command that does nothing.** `package.json:30-32` declares it in the Command Palette and `module.ts:75-83` implements it as an information message pointing at the sidebar, with the comment "kept for compatibility". Compatibility with what, given nothing was ever published (see 0011)? If nothing, it is a palette entry that only disappoints.

7. **Emoji shortcode rendering is a curated 40-entry map** (`utils.ts:63-102`) with unknown codes degraded to bare padded words (`utils.ts:110-121`) — `:kubernetes::rocket:` → `kubernetes 🚀`. Buildkite maintains a published emoji set (https://buildkite.com/docs/platform/emojis). Is the hand-curated map a deliberate bundle-size/no-dependency choice (consistent with 0013), or just what was needed at the time?

8. **The analysis prompt depends on an external, gitignored convention.** `jobAnalyzer.ts:56-57` instructs the assistant to "Use the context from .github/skills/\*\*/SKILL.md" and to cite it under "References" — while `.gitignore:6` ignores `.github/skills`. So the prompt targets files this repo deliberately does not contain. Is this an integration with a convention in the *user's* repository (in which case it is a documented feature and belongs in the README), or a personal workflow that leaked into a shipped prompt?

9. **`pnpm-workspace.yaml` declares a workspace file with no workspace.** It contains only `allowBuilds` (disabling postinstall scripts for `@vscode/vsce-sign` and `keytar`) and `overrides` pinning `diff` and `serialize-javascript` (`pnpm-workspace.yaml:1-6`) — there is no `packages:` key and no sub-package. The overrides look like security pins, and `allowBuilds: false` looks like a supply-chain stance. But whether "this is a monorepo-shaped repo" was ever intended, or this is just pnpm 10+'s home for those two settings, is not recoverable from the file.

10. **`renovate.json` is schema-only** (`renovate.json:1-3`) — no schedule, no grouping, no automerge, no pinning strategy. Combined with the caret ranges throughout `devDependencies` (`package.json:68-80`) and the exact pins in `.mise.toml:2-3`, the update policy is half-expressed. Default-Renovate-on-purpose, or enabled and never configured?

11. **`getJobLog` takes a URL it immediately discards.** `client.ts:273` accepts `logUrl`, parses it with a REST-path regex into pipeline slug / build number / job id (`client.ts:275-281`, `client.ts:110-128`), then passes all three to `bk job log` (`client.ts:285-296`). Per https://buildkite.com/docs/platform/cli/reference/job, `-p` and `-b` on `bk job log` are now documented as "Deprecated; ignored because job UUIDs no longer require pipeline or build context" — so two of the three parsed values are discarded by the CLI, and the whole URL-parsing step exists only to recover a job id the extension already has on `BkJob.id` (`client.ts:8`, `client.ts:350`). Was this written against an older CLI, or is `rawJobUrl` load-bearing for a reason I can't see?

12. **`BkState` is typed as an enum but compared as strings.** `client.ts:41-53` defines the enum, yet `BkJob.state` and `BkBuild.state` are plain `string` (`client.ts:9`, `client.ts:24`), forcing casts like `this.latestBuild?.state as BkState` (`module.ts:135`, `module.ts:688`) and string literals at `module.ts:40-48`, `module.ts:547`, `module.ts:554`, `jobAnalyzer.ts:94`. `'broken'` is filtered in the UI (`module.ts:547`) but is absent from the enum entirely, even though the REST API documents it (https://buildkite.com/docs/apis/rest-api/builds). Is the loose typing a deliberate hedge against Buildkite adding states, or just untightened?
